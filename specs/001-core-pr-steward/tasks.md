# Tasks: Core PR Steward (core loop and hosting)

**Input**: Design documents from `/specs/001-core-pr-steward/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/, quickstart.md, `.specify/memory/constitution.md` (v1.0.0)

**Scope**: This is spec 001 of four sequential specs cut from the original agent framework comparison. It owns original tasks T001 to T079 and T167 to T170 and T172 to T174, plus new tasks T175 to T179 (reserved range T175 to T199). Original task IDs are kept, so gaps in numbering are expected. Original tasks T080 to T166 and T171 belong to specs 002, 003, and 004. There is no reconciliation phase: this is the first spec.

**Tests**: Included. The constitution requires tests (Principle I) and a conformance suite that runs in CI against every implementation (Principle IX); the spec makes the conformance suite a deliverable (FR-022).

**Organization**: Tasks are grouped by user story. Stories are numbered as in spec.md. Phases here: 1 Setup, 2 Foundational, 3 US1, 4 US2, 5 US3, 6 Polish.

## Format: `- [ ] T### [P?] [US#?] Description with file path`

- **[P]**: can run in parallel with the other [P] tasks in the same step (different files, no dependency on an incomplete task). Where a step lists four tasks (one per implementation), the four are [P] with each other; steps within a phase run in the order listed.
- **[US#]**: user story from spec.md. Setup, Foundational, and Polish tasks have no story label.
- **⚠ needs owner approval**: task creates or destroys AWS resources, writes to GitHub with the owner's token, or spends money on live model calls. Stop and get explicit approval (with `tofu plan` output shown for infrastructure) before doing it. Everything else is local and safe.

## Path Conventions

Per plan.md: `implementations/<name>/` (Python: `src/steward/`, TypeScript for Mastra: `src/`), `shared/tool-server/`, `shared/conformance/`, `shared/db/`, `infra/{durable,edge,shared,tool-server,modules,implementations/<name>}/`, `specs/001-core-pr-steward/spikes/`.

## Constraints that apply to every task

- **No shared agent logic across frameworks** (constitution, Code Quality Gates): shared code is limited to the contract, fixtures, database migrations, stubs, tool server, conformance harness, and OpenTofu modules.
- **Framework facts come from current docs**, not memory (research.md marks UNVERIFIED items as spikes; this spec owns S2, S4 (scheduler part), S5 (MCP result part), S8, S10, S11, S12). Record surprises in the component's `CLAUDE.md`.
- **Definition of done for any implementation task**: tests written and passing, `ruff check` (Python) or `tsc --noEmit` (TypeScript) clean, and the exact commands and output recorded. Reports of "validated" without commands are not accepted (Constitution VIII).
- **Model access uses each framework's maintained Bedrock client** (`langchain-aws`, Claude Agent SDK Bedrock mode, `@ai-sdk/amazon-bedrock`, `pydantic-ai-slim[bedrock]`), never a hand-rolled `boto3` `invoke_model` wrapper (Constitution VII). A capability the client lacks is recorded as "not supported on Bedrock" (FR-023, FR-024) and appended to research.md section 6, not worked around and not routed to the Anthropic API.
- **Secrets**: credentials come from the environment or an AWS profile only and are never written to any file in the repository (Constitution V).
- **Independent verification**: a second actor (CI or a fresh worktree/session) reproduces each finished component's tests (Constitution I).
- **Deviations**: anything that differs from spec, plan, or contracts is written to `as-built.md` (T176) when it happens; spec 002 reads it.

## Dependencies & Execution Order

### Phase dependencies

- **Phase 1 (Setup)** has no dependencies.
- **Phase 2 (Foundational)** depends on Phase 1 and blocks every user story. Spike S12 (Bedrock, T013) runs first and gates every model-dependent task. The four S8 spikes (T015 to T018) follow because they decide whether the contract tier can use the stub model for each framework (risk R2).
- **Phase 3 (US1)** depends on Phase 2. Within it, per implementation the order is: model wiring (T030 to T033), skeleton (T036 to T039), worker and run recording (T040 to T043), logging and metrics (T044 to T047), summary agent (T048 to T051), unit tests (T052 to T055), then the checkpoint T056. T034, T035, and T177 are shared-lane tests that can be written as soon as the harness core (T025) exists.
- **Phase 4 (US2)** depends on US1 (it needs images to deploy) and contains the spikes S10 and S11. Infrastructure roots (T057 to T065) can be written in parallel with Phase 3 (they need only plan.md and the contracts) but cannot be applied before T056 passes and the owner approves. T066 and T067 need T057 to T065; T069 (S11) needs `bootstrap`; T070 (S10) needs deployed images; T175 needs T057 and T012.
- **Phase 5 (US3)** depends on US1 (worker registry, GitHub tools, tool-server client) and is independent of Phase 4 for its contract-tier work; the live `digest` scenario needs a deployment. The missed-digest alarm (`digest_alarm_enabled`, T061) is switched on once T075 to T078 have landed.
- **Phase 6 (Polish)** is last. T170 needs Phase 3; T172 and T173 need Phase 4 (T172 runs on the environment T072 left up; T173 is the only `destroy-all`); T178 needs everything.
- Tasks that edit the same file within one implementation (`worker.py`/`worker.ts`: T040 to T043 then T075 to T078; `admin.py`/`admin.ts`) are sequential in phase order for that implementation.

### Parallel lanes

Because the frameworks are independent, the most effective parallelism is one **lane per implementation** (LangGraph, Claude Agent SDK, Pydantic AI, Mastra), each working through the same steps, plus a shared lane (`shared/`, conformance tests) and an infrastructure lane (`infra/`, `justfile`). Recommended: one subagent per lane, each in its own git worktree, merging phase by phase.


## Implementation Strategy

1. Phase 1 and Phase 2 (foundations and spikes).
