## 2. Decisions

### D1. Language and runtime per implementation
- **Decision**: LangGraph, Claude Agent SDK, Pydantic AI in Python 3.13 (`uv`); Mastra in TypeScript on Node 22 LTS (`tsc` strict). Shared components (tool server, conformance/eval harness) in Python.
- **Rationale**: Matches the constitution's Technology Standards. Claude Agent SDK has a TypeScript SDK too, but Python keeps three of four implementations in one toolchain, and Mastra is the TypeScript representative.
- **Alternatives**: Claude Agent SDK in TypeScript (rejected: no comparison value beyond language); everything in TypeScript (rejected: LangGraph/Pydantic AI are Python-first).

### D2. Hosting: ECS Fargate for every component
- **Decision**: One ECS Fargate service per implementation plus one for the reference tool server, in a shared cluster behind one ALB with path prefixes (`/<impl>/...`), fronted by a long-lived CloudFront distribution so GitHub gets a stable HTTPS URL without the owner needing a domain. Fargate tasks run in public subnets with public IPs and tight security groups (no NAT gateway, which would add a fixed monthly cost); the database sits in isolated private subnets. Origin locked to CloudFront via a secret header.
- **Rationale**: All four need a long-lived process (Mastra's in-process scheduler, LangGraph workers, Claude Agent SDK's per-session subprocess, SSE streaming). One deployment shape keeps the deployment-effort comparison honest. Lambda was rejected for Claude Agent SDK (subprocess, disk transcripts) and Mastra (in-process cron).
- **Alternatives**: API Gateway + Lambda (rejected above); EKS (rejected: overhead); App Runner (rejected: weaker networking/SQS worker story); LangGraph Agent Server (rejected: license key, Redis, and it would hide the hosting effort the comparison wants to measure).

### D3. Shared vs per-implementation infrastructure (Constitution IV)
- **Decision**: Three layers, each its own OpenTofu root and state. **`infra/durable`** (survives teardown; see D18): S3 state bucket, ECR repos, Secrets Manager entries, artifacts bucket (eval reports), SNS alert topic, budget alarm, **VPC and subnets, and the Aurora Serverless v2 cluster (D4)**. **`infra/edge`** (also survives teardown): the CloudFront distribution, whose domain is therefore stable; only its origin is repointed by `up`/`down`. **`infra/shared`** (runtime, removed by `down`): ECS cluster, ALB, security groups, log groups. Each implementation is its own root (`infra/implementations/<name>`) with its own state: ECS service/task, target group + listener rule, SQS queue + DLQ, EventBridge Scheduler schedule, CloudWatch alarms, a reference to its database-role secret (`db-role/<schema>`, created in durable). `infra/tool-server` is a separate root. The durable layer also owns the migrate task (a small Fargate cluster, task definition, IAM, log group, and app-to-database security group) so schema and role creation and `db-reset` work while the runtime layers are down; it runs the `shared/db` image as a one-shot task with `assignPublicIp` enabled because there is no NAT.
- **Rationale**: Directly satisfies "apply or destroy one without touching the others". Remote state in S3 with lockfile-based locking, created by the durable root's first apply (`just bootstrap`).
- **Alternatives**: single root with `count` per implementation (rejected: violates independent state).

### D4. Datastore: Aurora Serverless v2 (scale-to-zero) Postgres, schema per implementation
- **Decision**: One **Aurora Serverless v2 (PostgreSQL) cluster with scale-to-zero** (minimum capacity 0 ACU, small maximum, automatic pause after a configurable idle period), one schema and role per implementation, plus a `toolserver` schema. It lives in the durable layer so data survives `down` with no snapshot/restore step. Used for: framework checkpoints/memory (LangGraph checkpointer/store, Mastra `@mastra/pg`, Pydantic AI harness memory + message history, Claude Agent SDK `SessionStore` + memory tool), webhook delivery dedupe, run records, approvals.
- **Rationale**: All four have a Postgres path; one engine means memory/durability differences are framework differences, not datastore differences.
- **Alternatives**: a plain RDS instance (rejected: hourly charge while running, must be stopped explicitly, and a stopped instance restarts itself after 7 days; declarative stop via OpenTofu also unverified); DynamoDB (rejected: LangGraph/Mastra storage adapters target Postgres); per-implementation database (rejected: cost).
- **Consequences of scale-to-zero** (all mitigated in the design): (1) resuming from pause takes on the order of 15 seconds (AWS figure from memory, verify in S11), so the **webhook handler MUST NOT touch the database before responding** (GitHub's delivery timeout is 10 seconds); it verifies the signature, enqueues, and returns 202, and the worker does the dedupe insert with connection retry (D5); (2) `/health` (used by the ALB every few seconds) MUST NOT query the database or it would keep the cluster awake; a separate `/ready` checks dependencies; (3) framework connection pools must not run keepalive queries that defeat auto-pause (S11); (4) workers and admin endpoints must retry connections for a short period.
- **Data across teardown**: the cluster is not part of `down`; only `destroy-all` deletes it (no final snapshot unless `KEEP_FINAL_SNAPSHOT=1`, which `verify-clean` reports as a declared exception). `FRESH=1` (or `just db-reset [impl]`) drops and recreates schemas instead of restoring anything.

### D5. Async work: SQS per implementation, uniform trigger for schedules
- **Decision**: The webhook handler verifies the signature (HMAC), enqueues a `WorkItem` carrying the delivery id on the implementation's SQS queue, and returns 202 **without touching the database** (see D4: the database may be paused). A worker loop in the same service consumes the queue, and its first step is an insert of the delivery id into a Postgres dedupe table (unique constraint), retrying the connection while the database resumes. Retries via SQS visibility timeout with a DLQ. The daily digest is triggered by an EventBridge Scheduler rule that enqueues a `digest` work item for the previous day.
- **Rationale**: Satisfies FR-010/011/012/013 the same way for all four, which lets the comparison focus on agent behavior. Uniform scheduling is deliberate: Mastra's native cron is single-process with unverified replica dedupe, and the digest must be exactly-once (User Story 3 scenario 3). Mastra's native cron is evaluated separately as a spike and recorded in the report, not used on the critical path.
- **Alternatives**: framework-native scheduling per implementation (rejected: makes the digest non-comparable and risks duplicates).

### D6. Model and providers
- **Decision**: **Amazon Bedrock for every model call** (agents, eval judge, helper models such as Mastra's observer), in all four frameworks, per spec FR-023 and the 2026-09-28 clarification. No Anthropic API key exists anywhere in the system and there is no fallback to the Anthropic API. Agents use Claude Sonnet 5.5, the judge uses Claude Opus 5.5 (a different, stronger model), and Mastra Observational Memory's observer is set to Claude Haiku 4.5 instead of the Gemini default; the exact Bedrock model or inference-profile IDs and the region are resolved in spike S12 and then pinned in configuration.
  - **Auth**: each ECS task role carries `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` (and Converse equivalents) scoped to the pinned model ARNs. The policy document is defined once in `infra/durable` (from its `bedrock_region` variable) and attached to each task role by the implementation module, so roots stay independent (Constitution IV). Credentials come from the task role through the standard AWS chain; nothing is stored in Secrets Manager for models.
  - **Client per framework** (docs-verified 2026-09-28, live behavior still S12): LangGraph via `langchain-aws` `ChatBedrockConverse` (Converse API; also `ChatAnthropicBedrock`); Claude Agent SDK via `CLAUDE_CODE_USE_BEDROCK=1` (**Invoke API only, no Converse**), `AWS_REGION`, pinned model env vars (`ANTHROPIC_DEFAULT_*_MODEL`), optional `ANTHROPIC_BEDROCK_BASE_URL`; Mastra via `@ai-sdk/amazon-bedrock` (credential chain includes ECS task roles; its `/anthropic` sub-provider uses InvokeModel with full Anthropic feature parity) instead of `anthropic/<model>` strings; Pydantic AI via `pydantic-ai-slim[bedrock]` (`bedrock:` prefix, `BedrockConverseModel`, `BedrockProvider` accepts a pre-configured boto3 client, native boto3 retries).
  - **Verified facts** (sources: AWS Bedrock model cards, Claude Platform "Claude in Amazon Bedrock" and Claude Code Bedrock docs, 2026-09-28): Sonnet 5.5 (launched 2026-09-28), Opus 5.5 and Haiku 4.5 are all in the Bedrock catalog. Sonnet 5.5 on `bedrock-runtime` is **global cross-region only** (ID `global.anthropic.claude-sonnet-5-5`; no in-region or geo profile in any US region), Converse and Invoke both supported. Opus 5.5 and Sonnet 5.5 access is not "open to all" (see model access in the console); Haiku 4.5 is open. Regional (non-global) endpoints carry a 10% premium. Default quota 2M input TPM. Claude Code lists Bedrock IAM actions `bedrock:InvokeModel`, `InvokeModelWithResponseStream`, `ListInferenceProfiles`, `GetInferenceProfile` on inference-profile, application-inference-profile and foundation-model ARNs (plus a Marketplace subscribe permission because these are Marketplace-billed models).
  - **Design consequence for the CI stub (D15)**: the Claude Agent SDK talks Invoke (`InvokeModelWithResponseStream`, binary `application/vnd.amazon.eventstream`) while LangGraph, Pydantic AI and (by default) Mastra talk Converse, so the stub must implement both wire formats, not one.
  - **Gating**: the decision is conditional on S12. If any framework cannot call Bedrock, the provider decision returns to the evaluator (spec Assumptions); it is not resolved here by falling back.
  - **Not supported on Bedrock (docs-verified)**: server-side tools (code execution, web search, web fetch), MCP connector, Agent Skills, programmatic tool calling, Files API and URL sources, Message Batches, structured outputs (Sonnet 5.5 card, both `bedrock-runtime` and Mantle), `count tokens` on `bedrock-runtime`, server-side fallback. Supported: streaming, prompt caching (min 512 tokens, 4 checkpoints, 5 min or 1 h TTL), thinking, client-side tool use including bash, text-editor and memory tools, citations, guardrails, 1M context on Sonnet 5.5. Server-side tool search is available only via the InvokeModel API, not Converse. Implications: Pydantic AI provider-side code execution is unavailable (US13 for that framework becomes "not supported on Bedrock"); use tool-call output rather than native structured output; Claude Agent SDK tool search works only because it uses Invoke; token usage comes from response usage fields, not a count-tokens call. Anything else Bedrock lacks is recorded as "not supported on Bedrock" in the report and not worked around (FR-024).
  - **Provisioning check**: `just doctor` and `deploy` verify that the pinned models are enabled for the account in the region and fail clearly there, not mid-run (spec Edge Cases).
- **Rationale**: Owner decision (spec): Taskrabbit runs on Bedrock, so the evaluation must reflect the environment it would adopt, even where that limits the frameworks; every resulting issue is logged in §6 and highlighted in the final report (FR-057). One provider for all four keeps model differences out of the comparison, and workload-identity auth removes model API keys from secrets handling. Cost: extra IAM and quota variables, and Bedrock lags the first-party API on some features, which is itself a finding.
- **Alternatives**: Anthropic API directly (rejected by the owner: Bedrock in the owner's AWS account is the required provider); Anthropic API as fallback for Bedrock gaps (rejected: FR-023 forbids it).

### D6a. Region
- **Decision**: `us-east-1` for all infrastructure and for `BEDROCK_REGION`, one region, not split. Fallback `us-west-2` (or `us-east-2` for a separate quota bucket). `AWS_REGION` and `BEDROCK_REGION` stay separate variables, both default `us-east-1`, and every OpenTofu root takes the region as a variable.
- **Why** (sources accessed 2026-09-28: AWS model cards for Sonnet 5.5, Opus 5.5, Haiku 4.5; Claude in Amazon Bedrock docs; Aurora Serverless v2 auto-pause and region docs): all three pinned models are available there; Sonnet 5.5 is served only through `global.anthropic.claude-sonnet-5-5` from every commercial region, so newer regions give no availability advantage for it (the claim that newer regions receive models sooner was not supported; the only early-mover pattern is the `bedrock-mantle` in-region endpoint, which is Messages-API-only and unusable by the Converse/Invoke frameworks, B4); Aurora Serverless v2 with scale-to-zero (PostgreSQL 16.3+/15.7+/14.12+/13.15+) and pgvector 0.8.0 are available; CloudFront certificates must live in `us-east-1`; splitting infra and Bedrock adds latency and inter-region transfer for no benefit.
- **Pinned global profiles** (verify in S12): `global.anthropic.claude-sonnet-5-5`, `global.anthropic.claude-opus-5-5`, `global.anthropic.claude-haiku-4-5-20251001-v1:0`.
- **Residency**: Sonnet 5.5 cannot be residency-pinned; Opus 5.5 and Haiku 4.5 have `us.` geo profiles. If Taskrabbit's Bedrock region differs, set `BEDROCK_REGION` to theirs.
- **Risks**: numeric RPM/TPM quotas were not retrievable and new accounts may start near zero (S12 checks Service Quotas and files increases before four-way concurrency tests); Haiku 4.5 shows a model end-of-life date no sooner than 2026-10-01 / 2026-10-16, so the Mastra observer needs a replacement plan; Fargate, ALB and Aurora prices and the EventBridge Scheduler region table were not verified.

### D7. GitHub access
- **Decision**: PyGithub (Python) and Octokit (`@octokit/rest`, `@octokit/webhooks` for signature verification) as the maintained client libraries (Constitution VII). PR data, digest issue creation, comment posting, and retrieval tools are thin tool wrappers over those libraries in each implementation. Exception, by design: the Claude Agent SDK implementation retrieves repo context idiomatically via a shallow checkout plus built-in Read/Grep/Glob, because that is the SDK's native strength; the report records the difference.
- **Rationale**: Uniform tool semantics with one deliberate idiomatic exception that is itself a finding. The GitHub MCP server via each framework's MCP client is a possible stretch, not on the critical path (langchain MCP client churn, Claude SDK static-token only).
- **Alternatives**: GitHub MCP server everywhere (rejected: conflates MCP-client quality with GitHub tooling, and MCP client evaluation is already covered by the reference tool server).

### D8. Reference MCP tool server
- **Decision**: Python, official `mcp` SDK (FastMCP), Streamable HTTP, bearer-token auth, Postgres `toolserver` schema. Tools: `record_pr_summary`, `record_review`, `record_digest`, `list_records`. Also plain HTTP `GET /records` for human inspection. See [contracts/mcp-tool-server.md](contracts/mcp-tool-server.md).
- **Rationale**: FR-004; tool discovery via `tools/list` must be exercised, so each implementation discovers the schema at runtime.
- **Alternatives**: existing hosted MCP server (rejected: no server chosen, and we need per-implementation attribution and inspection).

### D9. Agent-as-MCP-server and A2A
- **Decision**: Mastra uses `MCPServer` and native A2A. LangGraph, Claude Agent SDK and Pydantic AI wrap their agent in FastMCP (official SDK) and, for A2A, use the official `a2a-sdk` (Python) or `fasta2a` where it is the framework's own answer (Pydantic AI). Contracts in [contracts/agent-mcp-server.md](contracts/agent-mcp-server.md) and [contracts/a2a-specialist.md](contracts/a2a-specialist.md). The A2A specialist exposed is the same "risk reviewer" everywhere.
- **Rationale**: Wrapping cost is exactly what the report should record as **M**. Scoped to P3 per the clarification.
- **Alternatives**: skip A2A for frameworks without native support (rejected: FR-038 requires all four).

### D10. Approval mechanism (FR-015)
- **Decision**: The proposed PR comment is stored as an `ApprovalRequest`; the agent posts a "pending approval" comment; the owner approves or rejects by replying `/approve <id>` or `/reject <id>` on the PR (`issue_comment` webhook). Requests expire after 24 hours via a scheduled sweep (uniform EventBridge rule). Each framework suspends its run with its native mechanism (LangGraph `interrupt`, Mastra `suspend`, Pydantic AI `DeferredToolRequests`, Claude SDK `defer` hook + resumed session).
- **Rationale**: Uses only GitHub and existing webhook plumbing; no extra UI.
- **Alternatives**: Slack buttons (rejected: extra account).

### D11. Streaming and conversation (US7)
- **Decision**: `@steward` comment commands are handled through the same queue; progress is streamed by editing one PR comment at most every 2 seconds, and every implementation also exposes `POST /chat/stream` (SSE) for direct inspection. Only the repository owner may command (FR-017).
- **Rationale**: GitHub has no streaming primitive; edit-in-place is the practical equivalent, and the SSE endpoint exposes each framework's native stream shape.

### D12. Long context and memory (US15)
- **Decision**: Diffs over a configured token threshold are handled per framework with its idiomatic mechanism (LangGraph summarization/context editing, Claude SDK auto-compaction, Mastra Observational Memory, Pydantic AI `ProcessHistory`, and `AnthropicCompaction` only if S12 shows it works on Bedrock), with a shared fixture set of oversized PRs. Durable facts use each framework's native memory (LangGraph Store, Mastra memory, Pydantic AI Harness `Memory`) and a Postgres-backed in-process MCP tool for Claude Agent SDK. Every implementation exposes `/admin/memory` list/correct/delete ([contracts/http-api.yaml](contracts/http-api.yaml)). Facts are secret-scrubbed on write, stored with source, and capped (default 200 facts, oldest-least-used evicted).
- **Rationale**: FR-041..045; "native where it exists, manual where it doesn't" is what the report needs to record.

### D13. Observability
- **Decision**: JSON logs to CloudWatch Logs with `run_id`, `delivery_id`, `agent`, `tool`. Every implementation writes an `AgentRun` row (steps, model calls, tool calls, tokens, estimated cost, outcome) as the comparable source of truth; OTel export is best-effort per framework to an ADOT collector sidecar (traces to X-Ray). Metrics via CloudWatch EMF. Alarms: 5xx rate, failed runs, DLQ depth, digest-not-run (missing-data alarm), each to an SNS topic.
- **Rationale**: Framework OTel support is uneven (LangGraph without LangSmith and Mastra generic OTLP are UNVERIFIED), so comparable telemetry cannot depend on it. Constitution VI requires structured logs, metrics, and alerts.
- **Alternatives**: Langfuse/LangSmith/Logfire hosted (rejected: third-party accounts; can still be recorded as optional integrations).

### D14. Evaluation strategy (FR-019, FR-049, FR-050)
- **Decision**: Two layers. (1) **Shared harness** (`shared/conformance`, Python): fixtures (sample PRs with expected properties), contract tests, and an LLM-judge scorer (Opus) that emit the same JSON report for all four; runs against a deployed implementation. (2) **Native evals**, each in its framework's idiom: `pydantic-evals`, `openevals`/`agentevals`, Mastra scorers with `runEvals` in Vitest, and a manual eval for Claude Agent SDK. The report compares the two layers per framework.
- **Rationale**: FR-050 requires that the shared harness not mask native differences.

### D15. CI without live model cost (Constitution IX)
- **Decision**: CI runs the **contract tier** of the conformance suite against each implementation started in Docker Compose with a **stub Bedrock Runtime endpoint** (both Converse and InvokeModelWithResponseStream, the latter in binary event-stream framing, since the Claude Agent SDK uses only Invoke; each with streaming; reached by overriding the Bedrock Runtime endpoint URL, e.g. `AWS_ENDPOINT_URL_BEDROCK_RUNTIME`, or the framework's own base-URL setting), dummy AWS credentials, a stub GitHub API, and local Postgres/SQS (ElasticMQ or LocalStack). Covers signature checks, dedupe, work-queue, tool-server records, health, and the shape of every contract. The **live tier** (real Bedrock, real GitHub, deployed AWS) is run by `just eval <impl>` and its outputs are committed as evidence for the report.
- **Rationale**: Constitution IX needs conformance in CI on every push without spending on models. The stub is scoped to plumbing; it is not record/replay testing of agent quality (which stays deferred).
- **Risk**: A framework may not honour an endpoint override (the Claude Agent SDK's bundled binary, or the AI SDK provider in Mastra), or SigV4 signing against a stub may need care. Spike S8 verifies this early, on Bedrock.

### D16. Sandboxed execution (US13, optional)
- **Decision**: Spike only. ### D18. Spin-up, spin-down, pause (FR-051..056)
- **Decision**: The sanctioned primitives stay `just deploy|destroy|plan|smoke <component>` (Constitution II). On top of them, thin orchestration targets with identical behavior locally and in CI:
  - `just up [impl...]`: ensure `durable` (including the database) and `edge` exist; apply `shared`; apply `tool-server`; for each implementation, push the image only if its source digest is not already in ECR, run the durable migrate task for its schema, apply its root, wait for health; repoint the `edge` origin at the new ALB (`tofu apply -var origin_domain=<alb dns>`); run `smoke`; register GitHub webhooks (a no-op when the CloudFront domain is unchanged, the normal case); print URLs and estimated cost per day. `FRESH=1` resets the implementations' schemas first.
  - `just down [impl...]`: reverse order. Copy eval reports to the artifacts bucket. `down` with no arguments removes everything created by `deploy`, repoints the `edge` origin at an unavailable placeholder (clients get an error, not a stale ALB), and leaves only the durable and edge layers. The database keeps its data and pauses itself.
  - `just pause [impl...]` / `just resume [impl...]`: a `paused` OpenTofu variable sets each implementation's ECS desired count to 0, so state stays declared in code and not changed by ad-hoc CLI calls (Constitution IV). The database needs no action: with no connections it auto-pauses after the idle period. Resume needs no image rebuild. Pause leaves the ALB (fixed hourly cost) and the database storage.
  - `just status`: per component running / paused / absent, uptime, estimated $/day from task counts and recent database capacity use, whether the database is paused, and any leftover-cost warning.
  - `just destroy-all` then `just verify-clean`: also destroys the durable layer (its state bucket and secrets included; secrets use a zero recovery window) and, by default, leaves no snapshot; the only path that removes everything (FR-056).
- **Durable layers (survive `down`)**: `durable`: S3 state bucket, ECR repos and images, Secrets Manager entries, artifacts bucket, SNS topic, budget alarm, VPC/subnets, and the Aurora cluster with all data. `edge`: the CloudFront distribution (no idle charge; priced per GB and per request only). Estimated at a few dollars per month or less (database storage is the main item); documented in `infra/durable/CLAUDE.md` and `infra/edge/CLAUDE.md` with what each item costs. This is deliberate and satisfies Constitution II because `deploy`-created resources are all removed by `down`; the durable and edge layers are created by `bootstrap` and removed by `destroy-all`.
- **Forgotten-environment guard (FR-055)**: a monthly budget alarm to the SNS topic, and `just up MAX_UPTIME_HOURS=8` creates a one-shot EventBridge Scheduler entry that calls ECS `UpdateService` (desired count 0) through a scheduler universal target, so no extra Lambda is needed. The resulting drift is intentional and reported by `status`; the next `up`/`resume` reconciles it.
- **Webhook address**: CloudFront is its own long-lived layer, so its `*.cloudfront.net` domain is stable across `down`/`up` and the GitHub webhook stays registered; `up` still runs `webhook-register` (idempotent). Decided with the owner after confirming CloudFront has no idle charge. Caveat: the ALB gets a new DNS name on each `up`, so the distribution's origin must be updated, and a CloudFront configuration change still takes minutes to deploy; the gain is the stable URL and no create/delete of the distribution, not zero wait. If measured `up` time (S11) is too slow, the fallback is a long-lived ALB (about $16-20/month idle, an estimate) so the origin never changes.
- **Rationale**: One command each way, cheap idle state, and data survives teardown so memory and run history are not lost between sessions. The pause/down split gives a fast (minutes) stop for lunch breaks and a near-zero-cost stop for days.
- **Alternatives**: snapshot-and-restore of a plain RDS instance across `down` (rejected once Aurora scale-to-zero made keeping the database durable nearly free); single `destroy` only (rejected: loses data and forces slow rebuilds); leaving everything running (rejected: cost); ad-hoc `aws ecs update-service` for pausing (rejected: violates Constitution IV).

## 5. Cost note (informational)

Cost drivers, roughly in order: Fargate tasks, ALB (fixed, hourly), Aurora compute (only while active) and storage, CloudFront/CloudWatch (small), Bedrock model spend (on-demand token pricing per model; verify current Bedrock prices and quotas in S12). `pause` removes Fargate compute (the database pauses itself); `down` removes the ALB too, leaving only the durable and edge layers (mainly database storage, which is on the order of cents to a couple of dollars per month for a few GB, an estimate). Aurora Serverless v2 is billed per ACU-hour (about $0.12/ACU-hour in us-east-1 on the standard configuration, and about $0.10/GB-month storage; figures from memory, verify before deploying). Always-on at the 0.5 ACU floor would be roughly $44/month, more than a small RDS instance; with scale-to-zero the compute charge is only for active time. Rough always-on cost while all four are deployed: 5 Fargate services (0.5-1 vCPU each), the database, one ALB, CloudFront, CloudWatch/X-Ray, plus model spend. This is likely on the order of a few hundred dollars per month if left running, well above a few dollars per eval run; these are estimates, not measurements, so the plan's quickstart tears environments down with `just destroy` and SC-004 verifies nothing is left behind. Verify against the AWS pricing calculator before the first deploy.
