# Tasks: Agent Framework Comparison

**Input**: Design documents from `/specs/001-agent-framework-comparison/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/, quickstart.md, `.specify/memory/constitution.md` (v1.0.0)

**Tests**: Included. The constitution requires tests (Principle I) and a conformance suite that runs in CI against every implementation (Principle IX); the spec makes the conformance and evaluation suites a deliverable (FR-019, FR-022).

**Organization**: Tasks are grouped by user story. Stories are numbered as in spec.md, but phases run in dependency order: US8 (evaluation) and US9 (report) come last because they measure and describe everything else.

## Format: `- [ ] T### [P?] [US#?] Description with file path`

- **[P]**: can run in parallel with the other [P] tasks in the same step (different files, no dependency on an incomplete task). Where a step lists four tasks (one per implementation), the four are [P] with each other; steps within a phase run in the order listed.
- **[US#]**: user story from spec.md. Setup, Foundational, and Polish tasks have no story label.
- **⚠ needs owner approval**: task creates or destroys AWS resources, writes to GitHub with the owner's token, or spends money on live model calls. Stop and get explicit approval (with `tofu plan` output shown for infrastructure) before doing it. Everything else is local and safe.

## Path Conventions

Per plan.md: `implementations/<name>/` (Python: `src/steward/`, TypeScript for Mastra: `src/`), `shared/tool-server/`, `shared/conformance/`, `shared/db/`, `infra/{durable,edge,shared,tool-server,modules,implementations/<name>}/`, `docs/report/`, `specs/001-agent-framework-comparison/spikes/`.

## Constraints that apply to every task

- **No shared agent logic across frameworks** (constitution, Code Quality Gates): shared code is limited to the contract, fixtures, database migrations, stubs, tool server, conformance harness, and OpenTofu modules.
- **Framework facts come from current docs**, not memory (research.md marks UNVERIFIED items as spikes S1-S13). Record surprises in the component's `CLAUDE.md`.
- **Definition of done for any implementation task**: tests written and passing, `ruff check` (Python) or `tsc --noEmit` (TypeScript) clean, and the exact commands and output recorded. Reports of "validated" without commands are not accepted (Constitution VIII).
- **Model access uses each framework's maintained Bedrock client** (`langchain-aws`, Claude Agent SDK Bedrock mode, `@ai-sdk/amazon-bedrock`, `pydantic-ai-slim[bedrock]`), never a hand-rolled `boto3` `invoke_model` wrapper (Constitution VII). A capability the client lacks is recorded as "not supported on Bedrock" (FR-023, FR-024) and appended to research.md §6, not worked around and not routed to the Anthropic API.
- **Secrets**: credentials come from the environment or an AWS profile only and are never written to any file in the repository (Constitution V).
- **Independent verification**: a second actor (CI or a fresh worktree/session) reproduces each finished component's tests (Constitution I).

## Dependencies & Execution Order

### Phase dependencies

- **Phase 1 (Setup)** has no dependencies.
- **Phase 2 (Foundational)** depends on Phase 1 and blocks every user story. Spike S12 (Bedrock) runs first and gates every model-dependent task. The four S8 spikes follow because they decide whether the contract tier can use the stub model for each framework (risk R2).
- **Phase 3 (US1)** depends on Phase 2. **Phase 4 (US2)** depends on US1 (it needs images to deploy) and on the spikes S10/S11 it contains.
- **Phases 5-7 (US3, US4, US5)** depend on US1; they are independent of one another and can proceed in parallel per implementation. US5's reliability work touches the same worker files as US1-US4, so land US5 after US3/US4 for a given implementation, or merge carefully. More generally, [P] marks tasks that are parallel across the four implementations or across files; tasks that edit the same file within one implementation (`worker.py`/`worker.ts`: US1, US3, US4, US5, US6, US7; `admin.py`/`admin.ts`: US1, US6, US15; `summary.py`: US1, US10) are sequential in phase order for that implementation, and the test tasks that extend `shared/conformance/stubs/stub_bedrock.py` (US4, US5, US7, US10, US12, US15) are sequential in the same way.
- **Phases 8-13 (US6, US7, US10, US11, US12, US15)** depend on US1 and are mutually independent. US6 (approval) is reused by US12 (`requires_approval`); do US6 first. The Claude Agent SDK approval flow (US6) also depends on the SessionStore task (T089, US5). US15 builds on US7 (thread context) and US10 (retrieval).
- **Phase 14 (US13, optional)** depends on US4 (review) and a deployed environment.
- **Phase 15 (US14)** depends on US4 and on at least two implementations being deployed.
- **Phase 16 (US8)** depends on US1-US5 at minimum and is completed after the other stories so every scenario is measured.
- **Phase 17 (US9)** depends on US8 results and on whichever stories were completed; sections describing an unbuilt story must say so.
- **Phase 18 (Polish)** last.

### Parallel lanes

Because the frameworks are independent, the most effective parallelism is one **lane per implementation** (LangGraph, Claude Agent SDK, Pydantic AI, Mastra), each working through the same steps, with a fifth lane for shared components (`shared/`, `infra/`, conformance tests) and a sixth for the report once US8 output exists. Recommended lane owner assignment: one subagent per lane, each in its own git worktree, merging phase by phase.

## Implementation Strategy

### MVP first

1. Phase 1 and Phase 2 (foundations and spikes).
2. **US1 in one framework first** (recommended: Pydantic AI or LangGraph, the smallest hosting gap), proving webhook -> queue -> summary -> MCP record end to end with the contract tier, then replicate the same contract in the other three.
3. **US2** for that framework: deploy with OpenTofu, `just smoke`, `just down`/`up`. This proves hosting before more agent code is written.
4. Stop and validate: contract tier green in CI, one live scenario passing, one clean-state run of quickstart sections 1-4 by a second actor.

### Incremental delivery

Add P2 stories (US3, US4, US5) across all four frameworks, then the P3 breadth stories in the order listed, running the contract tier after each. Run live scenarios (⚠) only when the owner has approved spend. Finish with US8 and US9, then Polish.
